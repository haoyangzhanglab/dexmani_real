任务一：合同冲突

C-1 producer 就绪门 mode==6 AND accepts==1
CLAUDE.md "ARM_STATE 的 mode 是缓存 report 属性（必要非充分）；accepts_motion_commands 是 arm worker 写入的「当前接受伺服命令」单一事实……producer 就绪门是 mode==6 AND accepts==1，不能只看 mode"
AGENTS.md §3 不变量第 8 条："Only safety_state stores the SafetyState enum" 隐含 accepts_motion_commands 作为辅助 bit 存在

执行后变为 就绪门退化为 safety_state in (ARMED, RUNNING) AND not error_state AND is_running。Mode 和 accepts 不再是共享字段，producer 就绪门条款需要整条重写或删除。
受影响代码 policy/safety.py:184-216（feedback health 检查），teleop/loop.py:1276（accepts_motion_commands gate），utils/schema.py:129（ARM_STATE_DTYPE 字段）
C-2 ARMED/RUNNING 的 Mode-6 非阻塞 issue+confirm 进入
CLAUDE.md "ARMED/RUNNING 的 Mode-6 进入是非阻塞 issue+confirm（issue_mode_enter 发 set_mode(6)+set_state(0)，之后每 tick 用 mode_enter_ready 非阻塞确认），loop 不阻塞、每 tick 发布 accepts_motion_commands=0 直到确认；超 1.0s 走 error_state+stop_controller+EXIT"
指南冲突 1.1 "不要因为 DISARMED/ARMED/RUNNING 而切换 xArm Mode"；1.3 删除 issue_mode_enter()、mode_enter_ready()、_ModeTransition、mode_drift 全套；1.5 startup 一次性 set_mode(6) 后整个 runtime 保持 Mode 6
执行后变为 该条款完全废除。Mode 6 只在 startup 和 HOME 恢复时同步进入，不存在运行时非阻塞确认。CLAUDE.md 关于"转换窗口内瞬时 controller error 当作「未就绪」而非 fault"的细节也不再适用。
受影响代码 robot/arm_loop.py:619-653,887（issue+confirm 逻辑），robot/arm_sdk.py（issue_mode_enter/mode_enter_ready 函数）
C-3 arm queue 有序 maxsize=2
CLAUDE.md "arm queue 是有序 maxsize=2"
AGENTS.md §3 不变量第 6 条："The arm queue is ordered and intentionally bounded (maxsize=2)"
指南冲突 9.1 将 arm_action_q（有序 Queue）改为 arm_cmd_ring（latest-wins ring buffer）；理由是"机器人实时控制通常关心最新动作是什么，而不是每一个历史动作都必须执行"
执行后变为 arm 命令传输从有序 FIFO 变为 latest-wins ring。CLAUDE.md 和 AGENTS.md 关于 "arm queue 是有序 maxsize=2" 的条款需要改为 "arm command ring 是 latest-wins"。这与 hand command ring 的语义一致，但改变了 arm 的有序性保证。
受影响代码 shm/shared_storage.py:83,256,403（Queue 分配），utils/schema.py:72（ARM_COMMAND_DTYPE），policy/safety.py:521（queue put），teleop/loop.py（queue producer）
C-4 run_generation 控制时代协议
CLAUDE.md "run_generation 标记控制时代；BEGIN、pause、home、feedback fault 使旧命令失效。camera stall/写盘错误丢弃 episode，但等待下一次显式 BEGIN 才推进 generation"
AGENTS.md §3 不变量第 13 条："run_generation invalidates stale queued/ring commands across begin, pause, home, and feedback fault. Workers reject a command from an older generation before it crosses the command boundary."

C-5 worker 跨 SDK 边界复查 generation/有效期/状态/payload

C-6 普通 pause = command quiescence
CLAUDE.md "普通 pause 是 command quiescence：不发送 measured hold，不调用 State 4；让固件完成已接受的 endpoint"
指南冲突 1.2 DISARMED 采用 "software disarm"——停止发送命令，机械臂保持当前位置；9.4 不再引入 generation protocol，用 seq 新鲜度替代。指南未明确定义 "pause" 语义——DISARMED 是最接近的对应状态，但指南没有讨论 pause 期间已入队命令的处理。

C-7 SafetyGate 统一边界
CLAUDE.md "SafetyGate 是 action publish 的统一边界；固件仍是最后 backstop"
AGENTS.md §3 不变量第 15 条："deployment/coordinator.py is the sole robot-action producer and routes through the shared SafetyGate/send_command boundary"
指南冲突 6.1-6.3 SafetyGate 职责收窄为仅检查 action 本身安全性（shape/finite/joint limits/workspace/collision），删除 mode/accepts/connected/state_valid/feedback health/worker readiness 检查；6.3 生命周期 gate 简化为 is_running + not error_state + safety_state in (ARMED, RUNNING)；CommandPublishStatus 从十几种缩减为 SUCCESS/REJECTED 两三种

任务二：指南内部一致性

2a. 三种排序矛盾

指南存在三种不同的排序系统：阶段顺序（1→12）、推荐提交顺序（commit 01→12）、推荐执行优先级（P0→P9）。它们之间存在显著的对应错位。

A-1 P4 与阶段 1.4 的直接矛盾
矛盾描述 执行优先级 P4 将"删除 accepts_motion_commands / ARM_NOT_READY"排在 P3（统一 fail-fast error handling）之后。但阶段 1.4 已经在第一阶段就要求删除 accepts_motion_commands 和 CommandPublishStatus.ARM_NOT_READY。P4 是阶段 6（第六阶段）的内容，而 1.4 是第一阶段的内容。
影响 执行者无法判断：是在第一阶段就删（按 1.4），还是等到第六阶段再删（按 P4 优先级）？如果第一阶段删了，P4 就成了空操作；如果等到第六阶段，第一阶段的代码就无法编译（因为 1.4 已经删除了相关字段的使用者但字段本身还在 schema 中）。
A-2 commit 顺序与阶段顺序的错位
矛盾描述 commit 06 对应阶段 6（safety readiness 删除），commit 07 对应阶段 7（HOME 简化），commit 08 对应阶段 8（FK 移出）。但 P5 是 "HOME 去 RPC 化"（阶段 7），P6 是 "FK 移出 worker"（阶段 8），P7 是 "ARM state schema 瘦身"（阶段 5）。优先级排序把 schema 瘦身（阶段 5）推到了 HOME 和 FK 之后。
影响 三种排序系统产生三种不同的代码修改路径。执行者需要选择一种，但指南没有说明哪种是权威的。
A-3 P0-P3 与阶段 1-4 的隐含对应但 commit 05 不对应 P4
矛盾描述 P0=阶段1（删 Mode FSM），P1=阶段2（薄 XArm7），P2=阶段3（压缩 arm_loop），P3=阶段4（error handling）——前四个优先级与阶段 1-4 一一对应。但 commit 05 是 "simplify arm state schema"（阶段 5），而 P4 是 "删除 accepts_motion_commands / ARM_NOT_READY"（阶段 6 的内容）。P4 没有对应的 commit。
A-4 P7-P9 合并了阶段 5+9+10+11+12
矛盾描述 P7="ARM state schema 瘦身"（阶段 5），P8="command latest-wins"（阶段 9），P9="SharedStorage / config dead-code cleanup"（阶段 10+11）。但阶段 12（重新定义 SafetyState）在优先级排序中完全缺失。

2b. "不要做" 边界清单与后续阶段的自洽性

B-1 第一阶段"不要改 ARM_STATE_DTYPE 其他字段" vs 第五阶段删除字段
边界声明 第一阶段末尾："暂时不要修改：HOME transport / ARM_COMMAND_DTYPE / ARM_STATE_DTYPE 其他字段 / FK / SharedStorage"
后续阶段 第五阶段删除 connected、mode、tracking_err、state_valid、accepts_motion_commands 等大量 ARM_STATE 字段。这与第一阶段边界一致（第一阶段不动，第五阶段才动）。
自洽判定 自洽 第一阶段只删 accepts_motion_commands 一个字段（1.4），其余字段留到第五阶段。但 1.4 删 accepts_motion_commands 本身就违反了"不改 ARM_STATE_DTYPE 其他字段"的声明——这是第一个矛盾。
B-2 第一阶段"不改 SharedStorage" vs 第七阶段删 run_generation
边界声明 第一阶段不改 SharedStorage；第五阶段才开始动 IPC；第九阶段最后改 command transport
后续阶段 第七阶段 7.2 删除 run_generation（在 HOME transaction 上下文中）。但 run_generation 是 SharedStorage 的字段（shared_storage.py:164,261,406），第七阶段改 HOME 时不可避免地要改 SharedStorage。
自洽判定 部分矛盾 第五阶段才开始动 IPC 的边界与第七阶段删 HOME 中的 run_generation 不冲突（7 > 5），但指南没有明确说明第七阶段是否允许修改 SharedStorage。
B-3 第九阶段"最后做" vs 第十/十一/十二阶段
边界声明 第九阶段标题："第九阶段：最后再改 Arm Command Transport"，"这是最后一项结构性修改"
后续阶段 但还有第十阶段（删 SharedStorage arm-specific engineering）、第十一阶段（删冗余配置）、第十二阶段（重新定义 SafetyState）
自洽判定 可接受 "最后"指的是最后一项结构性修改，后续三个阶段是清理工作。措辞可以更精确。

2c. ESTOP 状态歧义

C-ESTOP 指南 1.2 的 ESTOP 语义与 SafetyState 枚举不一致
指南 1.2 列出五种状态语义：DISARMED / ARMED / RUNNING / FAULT / ESTOP，并说 "ESTOP → emergency_stop / state 4"
当前 SafetyState safety.py:14-20 只有四个值：DISARMED=0, ARMED=1, RUNNING=2, FAULT=3。没有 ESTOP。当前 e-stop 走 estop_request flag（AGENTS.md §3 第 8 条确认：estop_request 是简单 flag）。
歧义 指南没有明确说明 ESTOP 是：(a) 新增一个 SafetyState.ESTOP = 4 枚举值，还是 (b) 仅描述 e-stop 的行为（检查 estop_request flag → 调用 emergency_stop() → set_state(4)），ESTOP 只是行为标签而非状态值。
影响 如果是 (a)，需要修改 safety.py 的 SafetyState 枚举和 _ALLOWED_TRANSITIONS 表，并同步所有消费者。如果是 (b)，指南的列表格式误导读者以为 ESTOP 是一个独立状态。最终理想代码（第 2009 行）使用 shared.estop_request.value 检查 e-stop，暗示是 (b)，但 1.2 的列表格式暗示是 (a)。

2d. 验收标准的可验证性

D-1 "set_mode(6) 只在 startup 出现一次" 缺乏验证命令
指南给出 验收标准说 "set_mode(6) 只能在 startup 出现一次"，并给出验证命令：rg "set_mode|enter_mode|mode_enter|mode_transition|mode_drift"
问题 这个 rg 命令只能确认这些符号是否存在于代码中，无法验证运行时 set_mode(6) 是否只被调用一次。真正的验证需要：(1) 在 set_mode 调用处加 log/counter，(2) 运行完整生命周期并检查日志，或 (3) 静态分析所有 set_mode(6) 调用点确认只有 startup 和 HOME 两处。指南给了 rg 但没给出运行时验证方法。
D-2 各阶段验收标准详尽程度不一
问题 只有第一阶段给出了具体的验收标准（启动→Mode 6→DISARMED→ARMED→连续控制→…→shutdown 流程）。第二阶段到第十二阶段没有单独的验收标准节。"每个阶段的验证方法"（第 1863 行）给出了三层通用验证（静态/Fake SDK/真机），但不够具体——例如第四阶段（error handling）的验收应该包括"各种错误场景下 worker 正确 fail fast"，但没有列出。

2e. 最终理想 arm_loop 与各阶段要求的一致性

E-1 最终代码使用 SafetyState 但阶段 12 讨论可能废除
最终代码 第 2013 行：safety = SafetyState(shared.safety_state.value)，第 2015 行：if safety in (SafetyState.ARMED, SafetyState.RUNNING)
阶段 12 "如果后面继续化简，还可以考虑 enabled: bool / error_state: bool"——暗示 SafetyState 本身可能被两个 bool 替代
矛盾 最终理想代码仍然依赖 SafetyState 枚举，但阶段 12 暗示它可能被废除。读者不确定最终代码应该是"理想版"（用 SafetyState）还是"进一步化简版"（用 bool）。
E-2 最终代码未展示 estop 之外的异常处理细节
最终代码 只有 estop_request 检查和顶层 except Exception。没有展示：controller error 检查（4.2-D 要求每 loop 检查一次 arm.error_code != 0）、heartbeat 超时处理、safety_state 为 FAULT 时的行为。
矛盾 阶段 4.2 明确保留五类错误处理（初始化/state read/servo/controller error/shutdown），但最终理想代码只展示了 estop 和顶层 catch。controller error 每 loop 检查在概念代码中缺失。
E-3 最终代码使用 read_latest_command 但未定义其语义
最终代码 第 2016 行：command = read_latest_command(shared)
问题 指南 9.4 定义了 seq > armed_at_seq 的新鲜度检查，但 read_latest_command 函数在指南中没有定义。它应该包含 seq 检查、可选的时间窗口检查、以及返回 None 的条件。这是概念代码，但缺少关键 helper 的规格。
