# xArm7 真机诊断与控制机制验收记录

实验日期：2026-11-06。本文整理已完成的实验，供代码与实验结果 review；不是新一轮测试记录。

## 1. 结论

- **本次工况下，通信查询和 Ruckig 计算没有表现为明显瓶颈。** 保持与低速运动的有效发送频率约 98.6 Hz，稳定窗口没有通信超时，也没有超过 20 ms 的发送间隔。不能据此推断其他主机负载或动作配置下的表现。
- **首次准备的主要额外等待来自 SDK 碰撞参数设置。** 首次准备中位约 914 ms，再次准备约 341 ms；碰撞参数设置本身中位约 572 ms。首次设置阻塞期间的取消也要等待约 572 ms 才完成。
- **准备末尾第二次 `set_state(0)` 已删除并复测。** 保留模式切换后的第一次调用。成功准备每次减少一次 SDK 交互；再次准备中位仅减少约 0.3 ms，未证明稳定发送频率改善。
- **保持、普通停止、lease 到期和普通取消后的恢复均完成真机覆盖。** 结论限于裸法兰、J1 小幅低速运动及文中列出的重复次数。最终控制器处于 state 4，错误/告警均为零。

## 3. 测量方法与样本

### 3.1 路径与时间边界

- `read` 直接复用驱动的连接、读取和断开；不进入会发送停止命令的 owner 统一收尾流程。
- `hold`、`lifecycle`、`motion` 使用现有 driver、owner、邮箱、Ruckig 和停止流程，未另写伺服循环。
- 父子进程统一使用 `time.monotonic_ns()`；循环内记录内存数据，结束后导出。owner 数据通过共享内存读取，不经生命周期管道回传大块数据。
- 正常性能窗口不增加 SDK 查询；带额外 `get_state()` 查询的审计单独保存，不参与通信性能统计。
- 每轮性能测试预热 5 s，然后记录约 90 s 稳定窗口。有效频率按完整窗口的调用数 / 实际窗口时长计算；跨轮间隔不计入分布。本文三轮合并值按总调用数 / 总窗口时长计算，分位数由各轮窗口内样本合并得到。
- 反馈来源时间取查询开始；反馈年龄在 owner 使用该反馈生成/发送参考时记录，不能把读取缓存的时刻重盖为新样本时间。

这里的“SDK 耗时”是主机上的方法调用墙钟时间，包含 SDK、通道等待、通信及主机调度影响，**不是纯网络 RTT 或控制器精确接收时间**。SDK 返回成功和停止接纳都不等于机械臂到位。

## 5. 准备、模式切换与局部优化

### 5.1 为什么保留第一次、删除第二次 `set_state(0)`

状态审计与匹配版本源码给出的证据是：

1. `motion_enable()`、`set_mode()` 后仍可保持停止状态 4；模式切换后的第一次 `set_state(0)` 必须保留。
2. SDK 1.18.4 的 `set_collision_sensitivity()` 内部会等待任务并调用 `set_state(0)`；传入 `wait=False` 不能绕过该实现中的等待。其任务等待成功路径还包含固定 0.5 s 等待。
3. 两种模式的首次和后续准备中，末次参数设置 `set_joint_maxacc()` 后实测状态为可运行的 0 或 2，没有落入停止态 4。状态 2 与状态 0 数值不同，不能声称末尾 setter 从未改变过状态；判断的是它对本次准备流程是否必要。
4. 删除末尾调用后，同组首次准备、模式切换、取消、保持及 HOME 验收通过。审计中的 `get_state()` 是实时查询；异步 `mode` 缓存只作旁证，不单独作为切换成功的依据。

改动仅删除 [driver.py](../dexmani_real/robot/xarm7/driver.py) 中准备末尾的第二次调用及其紧随的重复取消检查；前面的取消检查仍保留，静态参数仍只在首次完整准备成功后复用。没有增加永久对照开关。

### 5.2 同条件准备耗时对照

下表时间为 **owner 的 operation 开始至结束**，包含准备后的停稳等待，不是单独的 setter 耗时。每种成功准备各 15 个样本。

| 指标 | 优化前 p50 / p95 / p99 / max，ms | 优化后 p50 / p95 / p99 / max，ms |
| --- | --- | --- |
| 新连接首次 Mode 1 准备 | 913.559 / 917.733 / 917.989 / 918.053 | 912.511 / 914.908 / 915.174 / 915.240 |
| 同连接再次 Mode 1 准备 | 340.898 / 343.523 / 344.369 / 344.580 | 340.596 / 341.293 / 342.188 / 342.412 |

15 组测试中的 `set_state` 总调用数由 **150 降至 120**，对应 30 次成功准备各省去一次调用。优化前碰撞灵敏度和负载各只设置 15 次，证明后续准备已复用静态参数；这项复用机制原本就存在，不是本次新增优化。

首次碰撞参数设置中位约 572 ms，与首次/再次准备约 573 ms 的差值吻合。去掉末尾调用没有消除这段 SDK 等待；准备总耗时差异也包含轮间波动，不能全部归因于补丁。

优化前运动三轮合并有效频率为 **98.604 Hz**，优化后一次 90 秒窗口为 **98.578 Hz**，没有证明稳定发送频率改善。

## 6. 取消、保持、停止与 lease

### 6.1 普通取消的两个时间尺度

优化前，同连接后续准备中的普通取消，请求至父进程完成收尾的中位约 **14.980 ms**，最大约 **16.156 ms**。取消若落在首次碰撞设置的阻塞等待中，结果不同：

| 首次准备等待中取消，15 次 | p50，ms | p95，ms | p99，ms | max，ms |
| --- | ---: | ---: | ---: | ---: |
| 优化前 | 571.514 | 574.464 | 575.457 | 575.705 |
| 优化后 | 568.360 | 573.274 | 573.530 | 573.594 |

这些取消均完成停止和回复消费，owner 保留并可再次显式准备。结果说明：**普通取消不能中断正在执行的阻塞 SDK 方法，20 ms 通信超时也不是整个准备函数的时间上限。** 真实故障、未决请求和中断的异常路径另由离线回归覆盖，未进行运动中断网试验。

### 6.2 停止处理与停稳确认必须分开

以下是 `after_motion90` 中的具体事件，**不是重复样本分位数**：

| 事件 | 事件 → 停止 SDK 开始，ms | 停止 SDK 调用耗时，ms | 事件 → 连续停稳确认，ms |
| --- | ---: | ---: | ---: |
| Ruckig 保持完成后的普通停止 | 0.873 | 0.285 | 354.965 |
| 运动中的普通停止 | 0.124 | 0.271 | 358.007 |
| 停止发布新目标 | 2007.772 | 0.486 | 2339.880 |
| HOME 执行中普通取消 | 0.059 | 0.288 | 未单独确认¹ |

¹ 该事件后很快开始下一次显式准备，离线统计在下一次操作处截断独立观察窗；空值不表示瞬时停稳，也不应拿后续准备中的样本补作独立停止精度证据。

“停止发布新目标”一行含原有 **2 秒 lease**。从停止发布至进入停止 SDK 约 2007.8 ms，其中约 7.8 ms 是超过 2 秒租期的量级；精确到期时刻应读取最后一次提交记录中的 `expires_ns`，不能把约 2008 ms 全部称为 owner 处理延迟。

本次独立停止观察窗中的停稳确认约 0.34～0.36 s，**包含 0.30 s 连续观测要求**。25 Hz 反馈约每 40 ms 一次，且查询有耗时，因此这些值不能解释成精确的物理制动时间。

在优化后运动复测中：

- 运动中发布保持请求后，实测停点与旧目标仍相距 **3.511°**，支持保持过程没有继续追赶旧位置目标的判断。
- 停止 SDK 接纳后、下一次显式准备前，记录到的伺服调用数为 **0**。
- lease 到期触发现有停止路径，随后能重新准备并执行新的目标。
- HOME 使用非零偏移，真实执行 Mode 0 运动并覆盖行程中取消，未将“回到当前位置而跳过运动”计为 HOME 覆盖。

## 7. 上层目标、参考与实测响应

稳定运动窗口每 2 秒切换 ±2° 目标，而 Ruckig 速度上限为 1°/s。因此参考通常尚未到端点就换向；目标与参考的较大偏差是该工况下刻意施加的规划限制，不能直接称为控制器跟踪误差。完整端点运动另用于保持、普通停止及 lease 测试。

反馈与参考按“反馈查询开始前最近一次主机参考”对齐，不插值，也未估计控制器精确接收时刻。J1 绝对位置偏差如下，单位为 **°**：

| 轮次 | 目标－参考 p50 / p99 | 实测－参考 p50 / p99 / max |
| --- | --- | --- |
| 基线 1 | 1.912 / 3.962 | 0.090 / 0.097 / 0.098 |
| 基线 2 | 1.866 / 3.947 | 0.088 / 0.096 / 0.098 |
| 基线 3 | 1.832 / 3.982 | 0.087 / 0.095 / 0.099 |
| 优化后 | 1.849 / 3.986 | 0.088 / 0.095 / 0.097 |

实测相对参考的偏差约 0.09°，不能直接除以设定速度就宣称控制器精确延迟为某个数值；这里同时存在反馈采样、主机参考对齐和控制器运动响应的影响。

![优化后目标、参考、实测及发送间隔](../logs/xarm_diagnostics/after_motion90/response.png)

图中灰色区域是稳定运动统计窗口，红色竖线标记普通停止请求。底部发送间隔排除了跨主动停止/HOME 边界的无发送时间，避免把生命周期间隙当作伺服抖动；完整时间线仍保存在原始数据中。

静止阶段各关节位置峰峰值约数个 `1e-6 rad`，速度残差约 `3.4e-5 rad/s`。这为停稳阈值提供了噪声参照，但仅凭裸法兰、单关节低速结果，不足以收紧全局阈值或缩短持续时间。本次保留原停稳判据与反馈频率。
