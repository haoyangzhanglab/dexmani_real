00核心论点

指南把目标明确定义为：删除 dexmani 自己构造出来的机器人控制状态机，让 arm 模块退化为一个薄硬件驱动。 它认为当前 arm_loop.py 的复杂性（Mode 转换状态机、就绪标志、drift 检测、多层错误升级、HOME RPC、在 worker 内跑 FK）是相互催生的软件状态，而不是机械臂的实际要求。

06指南自身的问题清单

按严重度排序。「高」= 不先解决会导致执行走偏；「中」= 执行中会撞上、需要临场决定；「已澄清」= 审计中曾怀疑、验证排除的问题。

高 — 执行前必须澄清

高三套顺序不一致：阶段顺序（1→12）、commit 顺序（01→12）、收益优先级（P0→P9）互相错位——P4（删 accepts/ARM_NOT_READY）横跨阶段 1.4 与 6；P7 才是 schema 瘦身（阶段 5）；P 列表完全没有阶段 12；P4 无对应 commit。执行者无法判断哪套是权威。
高ESTOP 语义歧义：1.2 把 ESTOP 与 DISARMED/ARMED/RUNNING/FAULT 并列为状态，但现 SafetyState 只有 4 值、e-stop 走 estop_request flag，最终理想代码也只用 flag。新增枚举值还是仅描述行为，未说明。
高is_hold 删了以后 hold 怎么表达：9.3 把 is_hold 列入删除，但 teleop 有 6 处靠它发 hold 命令、pause=quiescence 语义也依赖它。删除后 hold 行为的替代表达完全未定义。
高eef_pos/eef_rot6d 不在任何清单：5.1 保留清单没有、5.2 删除清单没有，只在 5.1 留了一句「FK 下一阶段处理」。这两个字段有 6+ 个消费模块，是最需要迁移计划的字段。
高action_id ↔ seq 关系未说明：9.2 目标字段叫 seq，9.3 删除清单不含 action_id；实际 action_id 就是序号字段。是改名还是删了重建，未说明（recording 多处消费 action_id）。
高episode schema 版本策略缺失：删 14 个 ARM_STATE 字段 + is_hold + tracking_error 是 episode v17 合同变更（writer/reader/processing/replay 同源约束），指南未说新版本还是仅影响新采集。

中 — 执行中会撞上

中最终理想代码的 finally 裸调 arm.stop(); arm.close()（l.2030–2031），与 2.6/3.4 要求的 try/except 保护矛盾。
中1.1/1.2 反复说「不要 set_mode」，但 2.2 的 connect() 序列本身含 set_mode(0)→set_mode(6)——措辞过于绝对，应表述为「runtime 不切换」。
中5.1 保留 error_code 发布，但 4.2-D 说每 loop 检查非零即 raise——保留在共享状态里的意义未解释。
中5.2 删 timestamp 未定义替代（recording/teleop 有 wall-clock / age 用途；现存两个消费者）。
中7.4 接受 HOME blocking 期间 servo loop 暂停，但若 heartbeat 在 loop 开头更新则期间心跳也停——与 5.3「heartbeat 代表 driver health」、保留 6 矛盾；且外部消费者在 HOME 期间收不到 state 更新，未说明。
中4.1 的 RetryCounter / ThrottledWarner 删除范围未说明 hand/teleop/planning 的共用边界（只应删 arm 实例）。
中缺测试策略（本仓库无常规测试套件，指南只给了三层 smoke）、缺回滚策略、缺合同文档同步步骤、缺 run_generation 保留边界的明文声明。
中ArmLoopConfig 实际定义在 arm_sdk.py（不在 config/）——阶段 2 删 arm_sdk.py 与阶段 11 删 ArmLoopConfig 存在先后耦合，指南未点明。

已澄清 — 验证排除的疑点

澄清「第一阶段不要改 ARM_STATE_DTYPE 其他字段」与 1.4 删 accepts_motion_commands 不矛盾——「其他」指其余字段（对抗验证纠正了审计的误读）。
澄清阶段 1「不动 FK」与阶段 8「移 FK」不矛盾——边界清单各阶段自洽（唯一例外是 eef 字段归类，见上）。

07梳理结论与使用建议

  1. 指南质量判断：可执行。它与代码现实高度吻合（点名符号 100% 命中、结构描述准确），哲学清晰（三个判断问题 + fail-fast + blocking 优先），阶段边界与「不要做」清单大部分自洽。
  2. 但它是一份「arm 模块内部删除计划」，不是完整操作指南。对 arm 之外 30+ 处引用的传播影响、合同文档同步、episode schema 版本、测试与回滚策略均无覆盖。执行前应把 §05 ripple 表逐阶段挂载为「消费者同步清单」。
  3. 先修指南再动手：指定唯一权威顺序（建议以 commit 顺序为准、P 列表仅作参考）；澄清 ESTOP / is_hold / eef 字段 / action_id↔seq 四个悬置点；在文中明文 run_generation 的保留边界（只出 HOME transaction 与 arm command metadata）。
  4. 建议的执行切分：第一轮做 P0–P3（Mode FSM → 薄 XArm7 → worker 压缩 → fail-fast），这是收益最大、几乎不碰 IPC 的部分，完成后复杂度即下降一半以上；第二轮再做 IPC/schema（阶段 5 起），并把 recording/data_processing 的字段迁移作为独立工作项。
  5. 每个 commit 附加合同同步：CLAUDE.md「不可破坏的协议」、AGENTS.md §3、docs/dataset/ 中对应条款随代码同 commit 更新（§04 的 7 条冲突是检查表）。
  6. 风险最高的单步是阶段 9（有序 Queue → latest-wins）：它同时改变 AGENTS §3.6 的架构不变量、pause 语义、以及与 hand 共用的 command 字段组。放在最后、单独验证是文档的正确判断。
