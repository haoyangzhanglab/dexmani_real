PF-DAG：支持研究生成一致性，不支持把所有跳变归咎于执行框架

论文将粗粒度动作模式选择与模式条件的 MeanFlow 生成分开，针对独立生成时可能出现的模式切换。其真实任务包含 xArm7 + XHand 的 Place Toy Into Bin；Figure 5(c) 的动作块消融呈现明显的反应性与稳定性折中，并非越短越好。这为当前块边界跳变提供了算法假设，而不是本次失败的因果证明。论文，Table 2、Figure 5(c)、§4.3。

公开代码要另看：README 明确标注 Early Access、可运行性未验证。检查到的 PFDAGPolicy.predict_action 是模式 argmax → codebook → VQ decoder 重建；相应 recon_action 直接调用 decoder。在本轮检查的公开策略源码中未找到完整的论文 MeanFlow 路径，不能将仓库现状等同于论文系统。

PolicyAgent 在队列空时同步预测，再弹出动作；虽然计算了 ensemble，实际入队的是原始 action_chunk，滑动平均也未启用。底层 机械臂线程 默认 50 Hz、Mode 1，从实测关节向目标限幅靠近；手线程 默认 100 Hz，也限制增量。因此表面简单的策略循环已经包含另一层目标处理。机械臂初始化还主动将碰撞灵敏度设为 0，这不应照搬到本项目。

保留 A=8/4/2 的对照建议，但同时统计成功率、边界目标变化和真实跟随，不能预设 A=2 最好。若统一执行条件后仍出现轨迹分叉，优先在 dexmani_policy 检验相同观测下的生成分布及相邻块重叠预测，再决定是否值得实现 PF-DAG 类解码器。当前日志不足以证明 mode bouncing，也不支持先新增执行层平滑来代替这个检验。

DexUMI：最值得借鉴的是时间与动作含义的一致性

DexUMI 显式区分传感器接收时刻与实际采集时刻；其训练处理校准传感延迟，再对齐模态。视觉与触觉进入策略，输出末端相对动作和手动作；这些设计服务于其外骨骼示教到机器人执行的转换。论文附录 E.2–E.3。

XHand 部署代码 用相机接收时间减去相机延迟作为动作时间基准，从历史机器人状态插值得到该时刻的末端位姿，再把预测变为世界坐标目标。随后按绝对目标时刻筛掉已经过去的动作，分别考虑臂与手的延迟。脚本默认相机 185 ms、臂 170 ms、手 300 ms，这些仅属于其设置，不能用于本项目的 RealSense/xArm/XHand。

策略循环默认 10 Hz 动作网格、每 8 步重推理，设备通过时间戳 waypoint 连续执行。server 入口 配置 UR5 500 Hz、手 30 Hz，分别使用位姿/关节插值。因此“同步预测”并不自动意味着设备每块停一拍；决定物理行为的是整个下发链路。

对本项目的新提醒是：相机 timestamp_ns 是主机队列返回时间，观测采样 检查各源主机新鲜度并保证点云/RGB 来源对应，但没有由此证明所有模态对应同一个物理时刻。此前 15–51 ms 的相机/点云年龄不能解读为完整曝光到策略延迟。J5 局部轨迹平移约 240 ms 可改善拟合，也只是该片段的相位描述，不能据此设固定补偿。

触觉处理同样要区分实际配置：enable_fsr 分支 对前三指读数阈值化并送入策略；示例训练配置 默认 enable_fsr=false。不能因为论文讨论触觉就假设每个 checkpoint 使用了它，也不能从非零触觉直接判定抓住物体。

先核对当前训练数据和 deployment 的 action 是否都表示相同的下发目标、dt、frame 与 joint ordering；在需要时测量设备时延，并让训练处理与部署保持一致。插值只有在明确改变数据配方的研究设计中才引入，派生缓存可重建，Raw 不改。SAM2、ProPainter、外骨骼重放解决的是异构示教的视觉差异，当前直接真机采集不需要增加这条流程。官方数据生成与部署说明。

RIO：借鉴异步调度，保留本项目已有的明确边界

policy_inference 在当前动作块耗尽前请求下一块；收到结果后按时间差计算已过去的 action index，不从第 0 项重新播放。PolicyInterface 通过请求队列和结果 ring buffer 解耦推理。这里的结果 timestamp 在 worker 收到请求、开始推理前产生，并不是相机曝光时间；时间索引正确与传感器物理对齐仍是两个层次。

xArm JOINT_POS 分支 使用 Mode 1，默认 250 Hz 独立伺服；目标经过带速度约束的插值，并在该分支启用默认 alpha=0.1 的低通。其运动连续性不能只归功于异步或少做校验。对当前 Mode 6 再叠加同样处理，会改变动态响应，应是另一个实验条件。

值得保留的验证在 RIO 也存在：policy/station action_space 匹配、向量形状、未来 target_time、SDK 返回码与设备 error。其 暂停恢复示例 会清本地 chunk，但该路径未见把 episode 代号随请求/结果传递；不能据此删掉本项目防止旧推理跨 episode 生效的 run_id。

整套迁移收益有限：多种 middleware、动态 Node/Client/Server 和跨机器人 action schema 服务于 RIO 的通用平台目标；当前 SingleArm.parse_action 仍按 arm + 单 gripper 解析并令 hand_cmd=None，并不是直接可用的 7+12 动作接口。论文报告的延迟优势也来自指定策略/硬件/对照路径，不能推广成“本项目换成 RIO 就会更快”。RIO 论文，§III–IV。

继续采用一个 I/O owner、一个串行推理 worker、一个当前计划和至多一个在途请求。借鉴按时间消费动作、阻塞任务不占控制线程；当前已经具备这些边界的大部分，无需重建通用 node 或 middleware。对普通 async 的名义时刻硬截止可作定点改进，但当前 sync session 没有触发该拒绝。

UFACTORY 插件：Mode 6 是可用路径，不能凭控制模式名称归因

官方驱动 对 joint 使用 Mode 6、Cartesian 使用 Mode 7；关节稳态下发为 set_servo_angle(..., wait=False)。首条同步动作会临时用 Mode 0 与 wait=True，前 20 条使用较慢速度。这和“必须 Mode 1 才能部署策略”的说法不符，也说明首动作、持续动作要分别分析。

eval_loop 是读取观测 → 同步 predict_action → send_action。文件虽留有 chunk smoothing 与 gripper lookahead 代码，SMOOTH_THRESHOLD=0，lookahead 使用处被注释；不是实际启用的连续性保障。它还要求部署 fps 与 dataset fps 一致，这是有物理意义的校验。

该代码也不适合作为本项目所有错误处理的模板：send_action 在 error_code 非零时直接返回传入 action，不能代表命令成功执行；稳态 SDK 调用未在该函数中根据返回码构造 dispatch 证据。当前 Raw 分开记录 action 与 dispatch 的做法更适合异常分析。

当前 Mode 6 的使用不构成已证实 bug；J5 跟随偏差依然是要解释的现象。先统一节拍和目标动态，再比较控制方式。若最终研究 Mode 1，需要连同伺服频率、插值、限速、停止行为及训练采集的一致性一起评估，不能只改 set_mode 参数。

重新归类：问题是什么，以及最小改动应落在哪里

本次现象/约束判断与证据强度建议
每 8 步固定等待一拍已确认的调度行为。推理约 26–38 ms，小于 62.5 ms；检查成本不是主要原因。相同模型、NFE=4、dt、A=8 下，先用现有普通 async、prefetch_steps=1 作对照；无需先增加 RTC。
动作块边界跳变策略与执行耦合。PF-DAG 支持模式切换假设，但本次缺少可区分模式切换与正常反馈修正的证据。确认索引后比较 A=8/4/2；同时看真实轨迹和成功率。平滑、temporal ensemble、RTC 都是需要标注的实验变量。
J5 明显跟随滞后已观察到现象；Mode 6 错误、固定传输延迟等单一成因均未证实。分开看目标时间、已下发目标、实测关节与设备动态；必要时单独测时延，不复制 DexUMI 常数或直接切 Mode 1。
tor_max_ma 的单位已确认的接口语义错误：Mode 3 的 tor_max 不是反馈电流 mA 的限值。按厂商当前模式定义修正命名、范围和日志解释；先保持数值。PF-DAG/DexUMI 使用 380/400 只能佐证用法，单位仍以厂商资料为准。
推开物体、闭合未夹稳、空手继续搬运任务失败，首先归入策略/训练覆盖/观测条件，调度和物理跟随可能放大失败。执行条件固定后检查策略；当前 ManiFlow 不用触觉。不要默认加抓取成功 FSM 或自动重抓，否则改变了被评估系统。
空手仍有触觉和持续电流涉及手内接触、负载、零位与机构因素，不能强塞进纯软件或纯策略一类；名义网格只支持接触可能性。继续区分手–物接触与手–手接触。真实异常码保留；不把触觉非零当抓取成功，也不一刀切禁止手自接触。
普通 async 固定 handoff 截止可简化的工程约束；代码上存在结果已可用于本拍但超过名义时刻仍被拒绝的可能，本次未发生。普通路径按实际可消费窗口、来源年龄及有效索引判断；RTC 承诺前缀的约束仅留在需要它的路径。
100 行 action NaN、严格导出拒绝有效实验记录与训练集准入不同。NaN 对应未调用 SDK，不是物理观测损坏。Raw 保留。遵守当前全部 13 字段完整的公共导出规则；若要让此类 rollout 回训，应明确设计等待动作及时间语义，不能填零/删帧。

“工程复杂度”不能只按代码行数或检查数量判断。可以去掉无当前需求的兼容分支、重复静态字典及多层 wrapper；字段/单位/normalizer 在加载边界检查，实时 freshness、授权和硬件限值在实际使用边界检查。run_id、来源时间、dispatch、失败前缀与 staging 保留使实验可解释，是科学正确性所需的复杂度。

结合项目策略需求的执行顺序

  1. 语义先正确：修正 tor_max 的单位口径，核对训练与部署使用的动作、dt、frame、joint ordering。不要把主机时间戳当曝光时间，也不要把 command 当 measured arrival。
  2. 用已有能力消除确定的节拍问题：相同 checkpoint/EMA/NFE=4/A=8，sync 对照普通 async、d=1。复核 SDK 间隔、动作来源年龄、chunk 边界跳变量和结果；这一轮不同时更换控制器或平滑。
  3. 再研究闭环更新频率：固定异步路径，比较 A=8/4/2。若还有跟随偏差，独立研究设备延迟/控制响应；若生成分叉仍突出，在 Policy 仓库检查解码器一致性。PF-DAG 与 RTC 不应同时混入一个无法归因的“修复”。
  4. 保护触觉研究的公平比较：本项目研究逐指几何与触觉融合，优先保持相同执行器比较无触觉、晚期融合和触觉参与几何读取。DexUMI 的简单触觉条件可启发基线；更复杂融合必须证明额外收益。PF-DAG 更换动作解码器是另一条研究轴，应与表征改动分开。

“好用”意味着入口突出模型、动作表示、dt、A 和是否预取，操作者无需理解未使用的 RTC 内部参数；日志能够直接区分策略任务失败、计划耗尽、设备故障和记录故障。它不意味着故障后自动恢复、自动松手或将失败记录加工成成功数据。
